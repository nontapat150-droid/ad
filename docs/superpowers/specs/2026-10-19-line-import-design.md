# แบบเชื่อม LINE กับ BO ad
วันที่ 19 ตุลาคม 2569 — ฉบับสำหรับตรวจและยืนยันก่อนพัฒนา

## เป้าหมายและสิ่งที่ผู้ใช้ระบุ
เพิ่มเมนูใน BO ad เพื่อรับข้อความปิดงานจาก LINE จัดเก็บข้อมูล ตรวจ SN กับสินค้าในระบบ หักจากกระเป๋าช่าง บันทึกประวัติ และดาวน์โหลด Excel ที่แยกประเภทชัดเจนและชื่อคอลัมน์ตรงกับข้อมูลต้นฉบับ
ผู้ใช้ยืนยันว่าช่างเจ้าของงานเป็นผู้ส่งเอง จึงใช้ LINE user ID ที่ผูกกับบัญชีช่างเป็นตัวระบุผู้ทำงาน ไม่ใช้ชื่อลูกค้า ชื่อเล่น หรือชื่อแสดงผลใน LINE มาเดาเจ้าของกระเป๋า

อ้างอิงโปรเจกต์ “อ่านและจดจำโปรเจกต์ BO ad” และตรวจโค้ดจริงที่ C:\xampp\htdocs\BO\ad:
- เว็บ React/Vite และ API Express/MySQL
- สินค้า inventory_items, inventory_models, inventory_products
- ประวัติ inventory_logs และการใช้กับงาน job_used_inventory / ma_job_used_inventory
- ระบบเดิมอนุญาตกระเป๋าทีม จึงต้องตรวจทั้งเจ้าของสินค้าและทีมของงานจริง
- มีงานขายที่แก้ค้างอยู่ในโฟลเดอร์เดียวกัน ต้องเก็บงานนั้นครบและแยกการเปลี่ยนแปลงชุดนี้

## ทางเลือกที่เลือกเสนอ (การตัดสินใจของผู้พัฒนา)
ต่อ LINE webhook เข้ากับ Express ของ BO ad โดยตรง ใช้ MySQL เป็นฐานข้อมูลหลักสำหรับการนำเข้าและการตัดอุปกรณ์ ไม่ตัดสต็อกจาก Google Sheets หรือเว็บตัวอย่างที่แยกอยู่
เหตุผลคือการเปลี่ยนสินค้า ประวัติ และผลนำเข้าสามารถยืนยันพร้อมกันในธุรกรรมเดียว และตรวจการปิดงานจากหน้าเดิมได้
Google Sheets ที่ให้ไว้ยังเป็นปลายทางรายงานตามขอบเขตเดิม การส่งรายงานต้องทำหลังฐานข้อมูลบันทึกสำเร็จและทำซ้ำได้โดยไม่เพิ่มแถวซ้ำ ความล้มเหลวของ Sheets ต้องไม่ตัดสต็อกซ้ำ ส่วน Excel ดาวน์โหลดจากข้อมูล BO ad โดยตรง

ทางเลือกอื่นที่ไม่เลือก: ให้ Apps Script หรือเว็บแยกส่งคำสั่งหักสินค้าเข้า BO ภายหลัง เพราะเพิ่มโอกาสที่ข้อมูลสองระบบไม่ตรงกัน

## ข้อจำกัดของ LINE ที่ต้องแสดงในเมนู
บอทรับข้อความใหม่เมื่ออยู่ในห้องที่อนุญาตและเปิด webhook แล้ว Messaging API ไม่มีช่องทางอ่านเนื้อหา Notes ทั้งกลุ่มหรือดึงประวัติข้อความเก่าทั้งหมด
ข้อความจาก Notes/ประวัติเก่าให้นำเข้าโดยคัดลอกข้อความ วางในเมนู หรืออัปโหลดไฟล์ TXT ที่ผู้ใช้ส่งออกเอง ไม่แสดงปุ่มที่อ้างว่าดึง Notes ย้อนหลังได้โดยตรง
รองรับเฉพาะข้อความตัวอักษรในรุ่นนี้ รูปภาพ/PDF/ลายมือไม่ถูกอ่านหรือเดาเป็น SN

- https://developers.line.biz/en/docs/messaging-api/group-chats

## หน้าจอและลำดับใช้งาน
เมนูผู้ดูแลชื่อ “นำเข้าข้อมูล LINE” ใช้สี รูปแบบ และเมนูของ BO ad เดิม แบ่งเป็น 4 ส่วน:
1. รายการนำเข้า: ค้นหาเลขงาน/Order/SN/ลูกค้า กรองวันที่งาน ช่วงวันที่รับข้อมูล ประเภทงาน ช่าง ทีม และสถานะ แสดงจำนวนรับแล้ว รอตรวจ ตัดแล้ว และข้อมูลซ้ำ
2. นำเข้าข้อความ: วางข้อความหรืออัปโหลด TXT ดูตัวอย่างแยกงานก่อนบันทึก แสดงว่าไฟล์ย้อนหลังยังไม่หักสินค้าโดยอัตโนมัติ
3. รอตรวจสอบ: เปิดเทียบข้อความต้นฉบับกับข้อมูลที่อ่านได้ เห็นช่าง งาน และผลตรวจ SN ทีละชิ้น พร้อมเหตุผลที่ยังไม่ตัด เลือกแก้การจับคู่ ตรวจใหม่ ยืนยันตัด หรือเก็บเฉพาะรายงาน
4. ตั้งค่าและประวัติ: ผูก LINE กับช่าง อนุญาตกลุ่ม/ทีม ดูสถานะ webhook และดูประวัติแก้ข้อมูล/ตัดอุปกรณ์/แก้การผูกบัญชี

ผู้ดูแล admin/super_admin ใช้สิทธิ์เดียวกับระบบคลังเดิม การตั้งค่าความลับอยู่ฝั่งเซิร์ฟเวอร์ ไม่แสดง token หรือ secret ในเว็บ/ไฟล์ Excel
ช่างส่งใน LINE ได้หลังผูกบัญชี ไม่มีสิทธิ์เลือกกระเป๋าคนอื่นผ่านข้อความ

ลำดับครั้งแรก:
- บอท BOT รับข้อความจากกลุ่มที่อนุญาต พร้อม LINE user ID
- ผู้ดูแลผูกผู้ส่งที่พบกับบัญชีช่างจริงและตรวจทีมให้ถูกต้อง บันทึกผู้อนุมัติและเวลาที่ผูก
- ข้อความที่มาถึงก่อนผูกบัญชีอยู่ใน “รอตรวจสอบ” การผูกภายหลังไม่ทำให้ข้อความเก่าถูกตัดสต็อกเอง ต้องตรวจใหม่และยืนยัน
- เปลี่ยนช่างหรือทีมที่ผูกเมื่อใดมีผลกับข้อความใหม่และการตรวจใหม่ ข้อมูลที่ตัดแล้วเก็บตัวตนและทีม ณ เวลาที่ทำรายการ ไม่ย้อนแก้ประวัติ

## ประเภทงานและการอ่านข้อมูล
รองรับ 4 ประเภทตั้งต้น:
- #ปิดงานติดตั้งais
- #ปิดงานติดตั้ง3bb
- #ปิดงานเปลี่ยนอุปกรณ์3bb
- #งานMA

อ่านวันที่ทั้ง 18/10/69 และ 18-10-69 เป็น 18 ตุลาคม 2569 สำหรับกรองข้อมูล พร้อมเก็บข้อความวันที่เดิมแยกไว้
ทนการเว้นวรรค ตัวพิมพ์ใหญ่เล็ก และเครื่องหมาย : ซ้อน เช่น Sn ONU : : ... แต่ไม่ตัดเลขศูนย์นำหน้าหรือเปลี่ยนหมายเลขให้เป็นตัวเลข
เก็บทุกช่องที่รู้จัก ช่องว่าง ช่องที่พบเพิ่ม ลำดับบรรทัด ชื่อหัวข้อเดิม และหัวข้อซ้ำตามลำดับ ไม่ทิ้งเพราะไม่มีในแบบฟอร์ม
บรรทัดต่อเนื่องที่ไม่มีหัวข้อเก็บเป็นส่วนหนึ่งของค่าหรือเป็นบรรทัดต้นฉบับที่ยังจัดไม่ได้ พร้อมคำเตือน ไม่เดาค่าเงียบ ๆ

ข้อมูลสองชั้น:
- ต้นฉบับ: ข้อความเต็มและ fields แบบมีลำดับ label/value/occurrence/line เพื่อส่งออกให้ตรง LINE และตรวจย้อนหลัง
- ค่าที่จัดรูปแบบ: ประเภท วันที่ เลขเคส Order/SRT ช่าง งาน และรายการ SN ใช้ค้นหา/จับคู่ ไม่เขียนทับต้นฉบับ

การจับคู่งาน:
- งานติดตั้ง/เปลี่ยนอุปกรณ์: ค้นหาใน jobs ด้วยเลขเคส/Access และ Order no / customer order ที่ระบบมี ต้องสอดคล้องกัน
- งาน MA: ค้นหาใน ma_jobs ด้วย NON/Access และ SRT ต้องสอดคล้องกัน
- กำหนดให้ตรงเพียงงานเดียว และช่างผู้ส่งเป็นผู้รับผิดชอบหรืออยู่ทีมเดียวกับงานตามสิทธิ์เดิม
- พบหลายงาน เลขอ้างอิงขัดกัน หรือไม่มีงาน ให้เก็บข้อมูลแล้วรอตรวจ ไม่สร้าง/ปิดงานใหม่เอง

## กติกาตรวจ SN และหักกระเป๋า
ข้อความใหม่ที่เข้า webhook หลังเปิดใช้อัตโนมัติจะหักได้เมื่อครบทุกเงื่อนไข:
1. ลายเซ็น LINE ถูกต้อง กลุ่มได้รับอนุญาต ผู้ส่งผูกกับช่างที่ยังใช้งานอยู่ และมีประเภท/วันที่/เลขงานที่อ่านได้
2. จับคู่งานได้แน่นอนและผ่านสิทธิ์ช่าง/ทีม
3. ทุก SN ที่ต้องใช้ระบุชัด พบสินค้าเพียงหนึ่งรายการใน inventory_items และชนิดอุปกรณ์สอดคล้องกับช่องในข้อความ
4. สินค้าอยู่ในสถานะ dispatched มีจำนวนพอ ไม่หมดอายุ และอยู่ในกระเป๋าช่างหรือกระเป๋าทีมเดียวกับงานตามกติกาเดิม
5. ถ้าตัดใช้กับงานนี้ไปแล้ว ให้บันทึกว่า “เคยใช้กับงานนี้แล้ว” ไม่หักอีก ถ้าใช้กับงานอื่น รอตรวจ

ตัดเฉพาะอุปกรณ์ใหม่/อุปกรณ์ที่ติดตั้ง เช่น Sn ONU, Sn Playbox, Sn Mesh, Sn Mesh เช่า, Sn Sim, Sn IP Camera และ SN ใหม่ ของงาน MA
SN เก่า ของ MA เก็บไว้เป็นข้อมูลเท่านั้น ไม่หักและไม่รับคืนเข้าคลังโดยอัตโนมัติ
SOA ที่เป็นชื่อรุ่น เช่น Active+FibreHome ไม่ถือเป็นหมายเลข SN และไม่เดาสินค้าคงคลังจากชื่อรุ่น
ช่องว่าง - หรือไม่มีอุปกรณ์ใหม่ ไม่สร้างรายการหักเทียม แต่ถ้ามีข้อความที่อ้างว่ามีอุปกรณ์ใหม่แล้วระบุ SN ไม่ชัด ให้รอตรวจ
สาย ตัวต่อ และอุปกรณ์ไม่มี SN เก็บรายงานไว้ก่อน ต้องเลือกสินค้ารุ่น/หน่วย/จำนวนจากระบบอย่างชัดเจน จึงค่อยยืนยันใช้ผ่านกระบวนการเดิม ไม่แปลงระยะสายเป็นยอดหักเอง

SN ซ้ำในข้อความเดียวกันเก็บต้นฉบับครบ แต่หักชิ้นเดียวเมื่อบทบาทตรงกัน ถ้า SN เดียวอยู่คนละบทบาท หรือช่องเดิมมีหลายค่าที่ตีความกำกวม ให้รอตรวจ
ถ้ามีหลาย SN แล้วผิดเงื่อนไขแม้แต่ชิ้นเดียว ให้ทั้งงานรอตรวจ ไม่ตัดเพียงบางชิ้นเงียบ ๆ

กระเป๋าทีม: ใช้ขอบเขตเดียวกับกติกาคลังเดิมของ BO ad แสดงเจ้าของสินค้าเดิม ช่างผู้ส่ง และทีมในประวัติแยกกัน ไม่ย้ายเจ้าของเพื่อทำให้ผ่านการตรวจ
เปรียบเทียบ SN โดย trim และไม่สนตัวพิมพ์ใหญ่เล็กเพื่อค้นหา แต่เก็บค่าต้นฉบับ ไม่ลบช่องกลาง/เครื่องหมายอื่นหรือเดาเลขที่อ่านไม่ชัด หากฐานข้อมูลมี SN ซ้ำหลายรายการ ให้ผู้ดูแลแก้ก่อน

ไฟล์ย้อนหลัง/ข้อความที่วางเอง: บันทึกและสรุปได้ แต่ต้องเลือกช่างและงานและยืนยันรายการหักหลังดูตัวอย่าง แม้ข้อความจะมีชื่อผู้ส่งจาก TXT ก็ไม่ใช้เป็นหลักฐานผูกบัญชี LINE
สำหรับข้อความใหม่ ผู้ดูแลตั้งเริ่มต้นเป็นโหมดตรวจอย่างเดียวระหว่างติดตั้ง แล้วเปิด “ตัดอัตโนมัติ” หลังผูกกลุ่มและช่างและผ่านทดสอบจริง จึงลดปัญหาจากประวัติเดิม

## ธุรกรรมและการทำงานร่วมกับหน้าปิดงานเดิม
การรับ webhook บันทึก inbox ลง MySQL ก่อนตอบสำเร็จ ใช้ webhookEventId เป็นคีย์กันซ้ำ เปิดใช้ redelivery ได้ งานประมวลผลอ่าน inbox ที่ค้างและเริ่มใหม่หลังเซิร์ฟเวอร์หยุดได้ ไม่อาศัยหน่วยความจำอย่างเดียว
payload หลาย events ต้องเก็บครบในธุรกรรมรับข้อมูล การบันทึกล้มเหลวตอบไม่สำเร็จเพื่อให้ส่งซ้ำ การตรวจลายเซ็น HMAC SHA256 ใช้ raw bytes ก่อน JSON parser
ไม่บันทึก reply token/secret ลง log หรือ Excel เก็บข้อมูลผู้ส่งและห้องเท่าที่จำเป็น

การประมวลผลต่อหนึ่งงาน:
- ล็อกแถวงานและ inventory_items ตามลำดับที่แน่นอนในธุรกรรม ตรวจทุกเงื่อนไขซ้ำขณะล็อก
- เปลี่ยนสินค้า บันทึก inventory_logs บันทึกการใช้ใน job_used_inventory หรือ ma_job_used_inventory บันทึกผลนำเข้าและ audit สำเร็จพร้อมกัน
- มีคีย์ไม่ซ้ำสำหรับ event, รุ่นข้อมูล และผลการตัดที่ยังมีผลอยู่ เพื่อกันการส่งซ้ำ/ผู้ดูแลกดยืนยันพร้อมกัน/การ retry
- deadlock หรือปัญหาชั่วคราว retry แบบจำกัด หากยังไม่สำเร็จแสดงปัญหาและรันใหม่ได้

ขอบเขตที่ผู้พัฒนาเลือก: การนำเข้าไม่เปลี่ยนสถานะ jobs/ma_jobs เป็น completed ไม่สร้างค่าจ้าง น้ำมัน ค่าแรกเข้า หรือรูปหลักฐานแทนช่าง เพราะผู้ใช้ขอรับข้อมูลและหักสินค้า ไม่ได้ขอข้ามเงื่อนไขปิดงานเดิม
แต่ต้องเชื่อมกับหน้าปิดงานเดิมอย่างครบถ้วน:
- หน้าปิดงานเห็นอุปกรณ์ที่ใช้จาก LINE แล้ว และส่ง/บันทึกอุปกรณ์ชุดนั้นได้โดยไม่หักซ้ำ
- เส้นทาง API ปิดงานและใช้สินค้าเดิมต้องล็อกงานเดียวกันและตรวจประวัติใช้ก่อน เพื่อกันชนกับ webhook ไม่ใช่แก้เฉพาะในเมนู LINE
- ปิดงานจากหน้าเดิมก่อนแล้ว LINE มาทีหลัง: ถ้า SN/งานตรงกับประวัติ ให้เชื่อมประวัติเดิมและไม่ตัดซ้ำ
- LINE ตัดก่อนแล้วช่างปิดงาน: เก็บรายการใช้เดิมและเติมได้เฉพาะชิ้นใหม่ที่ผ่านเงื่อนไขเดียวกัน
- การแก้การจบงานโดยแอดมินที่เดิมคืนแล้วตัดใหม่ต้องคำนึงถึงรายการที่มาจาก LINE อัปเดตสถานะผลนำเข้าให้ตรงจริง หากอุปกรณ์ถูกคืนแล้ว การ retry ข้อความเก่าต้องไม่ตัดกลับเอง
- เส้นทางตัดอุปกรณ์อื่นของงานเดียวกันต้องไม่ทำให้เกิด usage ซ้ำจากการประมวลผลพร้อมกัน
- ไม่เปลี่ยนวิธีปิดงาน MA ที่ต้องมีรูป และไม่ให้ข้อความ LINE ปลดข้อกำหนดนั้น

## ข้อมูลซ้ำ การแก้ไข และประวัติ
- event เดิมส่งซ้ำ: ไม่เพิ่มแถวงานหรือรายการตัดซ้ำ
- ข้อความเดิมถูกส่งใหม่: ตรวจ hash ร่วมกับกลุ่ม/ช่าง/เลขงาน พร้อมตรวจการใช้สินค้าเดิม
- เลขงานเดียวกันแต่เนื้อหาต่าง: เป็นรุ่นใหม่รอตรวจ ไม่เขียนทับหรือตัดเพิ่มทันที ผู้ดูแลเลือกเก็บเดิม/รับข้อมูลแก้ไข
- แก้เฉพาะรายงาน เช่น ชื่อลูกค้าหรือหมายเหตุ: บันทึกก่อน-หลังและผู้แก้ ไม่มีการเปลี่ยนสต็อก
- เปลี่ยน SN หลังตัดแล้ว: ในรุ่นแรกต้องแก้ผ่านขั้นตอนคืน/เปลี่ยนอุปกรณ์ของระบบเดิมโดยผู้มีสิทธิ์ แล้วให้ระบบ LINE ตรวจและเชื่อมผลใหม่ ไม่ลบหลักฐานหรือคืนเข้าคลังเองจากการแก้ข้อความ
- ข้อความที่ unsend หลังประมวลผล: บันทึกสถานะว่าถูกถอน แต่ไม่ย้อนสต็อกอัตโนมัติ ไม่แสดงเป็นข้อมูลรับรองปัจจุบันโดยไม่แจ้งเตือน
- ประวัติแสดงแหล่งข้อมูล เวลาข้อความ เวลารับ ผู้ส่ง/ช่าง/ทีม งานที่จับคู่ SN เจ้าของเดิม จำนวนก่อน-หลัง ผู้อนุมัติหรือระบบอัตโนมัติ เหตุผล และ reference ไปยัง inventory_logs

## ฐานข้อมูลที่เพิ่ม (โครงร่างสำหรับผู้พัฒนา)
แยกตารางสำหรับ:
- กลุ่ม LINE ที่อนุญาตและทีมที่เกี่ยวข้อง
- การผูก LINE user ID กับ BO user และประวัติเปลี่ยนการผูก
- durable webhook inbox, สถานะ retry, event ID ไม่ซ้ำ
- ข้อความนำเข้า/รุ่นข้อมูล/ข้อความต้นฉบับ/ordered fields/ค่าที่จัดรูปแบบ/แหล่งนำเข้า
- รายการ SN ที่แยกได้ ผลตรวจ และการอ้างอิงสินค้า/งาน/usage/log
- ประวัติการอนุมัติ แก้ไข และผลตัด/คืน พร้อม unique active effects
- คิวส่งรายงาน Google Sheets หลังบันทึกสำเร็จ
ใช้ migration ชัดเจนและนำกลับ/ยกเลิกได้โดยไม่ลบประวัติคลังเดิม ไม่ใช้ schema snapshot เก่าที่ชื่อสินค้าไม่ตรง routes ปัจจุบัน
ชื่อคอลัมน์ รายละเอียด index และวิธีเก็บ JSON ที่รองรับ MySQL/MariaDB รุ่นใช้งานจริงเป็นการตัดสินใจของผู้พัฒนา มีเอกสารประกอบ

## Excel และ Google Sheets
ปุ่ม “ดาวน์โหลด Excel” ใช้ตัวกรองเดียวกับรายการ เลือกวันที่ตามวันติดตั้ง/วันที่แก้ไข เริ่มต้นรวมวันต้นและปลายทั้งวัน
Excel หนึ่งไฟล์แยกแผ่นงานเป็น ติดตั้ง AIS / ติดตั้ง 3BB / เปลี่ยนอุปกรณ์ 3BB / งาน MA พร้อม สรุป / ประวัติอุปกรณ์ / ข้อความต้นฉบับ
แต่ละแผ่นงานประเภทใช้เฉพาะช่องของประเภทนั้น หนึ่งแถวต่อหนึ่งข้อความ/รุ่นที่เลือก ไม่ผสมหัวข้องาน MA ลงในติดตั้ง
ชื่อหัวคอลัมน์ใช้ label ของต้นฉบับ ไม่แปลงเป็นอังกฤษ ไม่เปลี่ยนคำผิดใน LINE ให้หายจากรายงาน รักษาตัวพิมพ์และคำที่ต่างกันตามต้นฉบับ เช่น แพ็กเกจ / แพ็กเกจหลัก
ตัดเฉพาะตัวคั่น : และช่องว่างรอบหัวข้อออกจากชื่อคอลัมน์ คำในหัวข้อยังตรงต้นฉบับ ถ้าต้องรวมคำพ้องเพื่อสรุป ใช้ในแผ่นสรุปแยก
ลำดับคอลัมน์อิงแบบตัวอย่างที่ผู้ใช้ส่ง และเติมหัวข้อที่พบเพิ่มตามลำดับแรกที่พบ
หัวข้อซ้ำ เช่น Sn ONU สองครั้ง ใช้สองคอลัมน์ที่แสดงชื่อหัวข้อเดิมซ้ำตามลำดับ (ตำแหน่งแรก/สองเก็บเป็น key ภายใน) ไม่รวมให้ SN ตัวหนึ่งหายและไม่เติม suffix เข้า label โดยไม่แจ้ง
ช่องว่างอยู่เป็นช่องว่าง และเลขเคส Order/SN/SRT เก็บเป็นข้อความเพื่อไม่เสียเลขศูนย์หรือกลายเป็นเลขยกกำลัง
วันที่ในแผ่นประเภทเก็บรูปแบบที่ช่างเขียน ส่วนวันที่มาตรฐานใช้ในแผ่นสรุปและการกรอง
แผ่นประวัติอุปกรณ์เพิ่มคอลัมน์ของระบบ เช่น ช่าง ทีม ผลตรวจ สถานะตัด เวลา และเลขอ้างอิง log โดยไม่สอดแทรกในรูปแบบข้อมูล LINE หลัก
รายงานค่าเริ่มต้นใช้รุ่นที่รับรองล่าสุด ไม่รวมรุ่นขัดแย้ง/ปฏิเสธเป็นผลงานซ้ำ ข้อมูลที่รับมาแต่รอตรวจยังส่งออกได้ผ่านตัวเลือก “รวมรายการรอตรวจ” และแสดงสถานะในแผ่นสรุป
แผ่นข้อความต้นฉบับเก็บทุกรายการตามตัวกรอง รวมเหตุผลที่อ่านไม่ได้หรือรอตรวจ เมื่อข้อความเกินขนาดช่อง Excel ให้แยกเป็นหลายแถว/ส่วนโดยไม่ตัดทิ้ง
ค่าที่ผู้ใช้พิมพ์ขึ้นต้น = + - @ ส่งออกเป็น string cell ไม่รันเป็นสูตร
Google Sheets ใช้ข้อมูลที่รับรองและคีย์นำเข้าเดียวกัน แยกประเภท/ข้อมูลอุปกรณ์และสถานะให้ชัดเจน การตั้งค่าปลายทางต้องไม่ให้ client ระบุ spreadsheet อื่นได้ตามใจ

## การตรวจรับ
- ตัวอย่างครบ 4 ประเภท วันไทยสองรูปแบบ ช่องซ้ำ : ซ้อน ข้อมูลเพิ่ม และ SN หลายชิ้น
- ผู้ส่งที่ยังไม่ผูก กลุ่มไม่อนุญาต และผู้ส่งคนละทีม ต้องไม่หัก
- SN ตรงกระเป๋า/กระเป๋าทีม SN ซ้ำใน DB สินค้าหมดอายุ ถูกใช้กับงานอื่น หรือชนิดไม่ตรง
- ทุก SN ผ่านจึงตัดครบ ถ้าชิ้นหนึ่งผิดต้องไม่เกิดผลหักบางส่วน
- webhook ส่งซ้ำ ข้อความเดิมส่งใหม่ ยืนยันซ้ำพร้อมกัน และ worker หยุดหลัง commit ก่อนตอบ
- หน้าเดิมปิดงานก่อน/หลัง LINE และแอดมินแก้การจบงาน ต้องไม่ตัดซ้ำหรือคืนสินค้าค้างผิดรายการ
- MA SN เก่าไม่ถูกหัก และการไม่มีรูปไม่ทำให้ระบบปิดงาน MA แทน
- Excel แยกประเภท หัวข้อ/ลำดับ/ช่องซ้ำครบ เลขยาวเป็นข้อความ ตัวกรองวันรวมต้น-ปลาย
- สิทธิ์ API เป็นจริงฝั่ง server ไม่พึ่งแค่ซ่อนเมนู
- ทดสอบโค้ดและ DB บนชุดทดสอบแยกก่อนแตะข้อมูลจริง ไม่ใช้สินค้าของช่างจริงทำ smoke test

## ขั้นตอนส่งมอบ
1. ยืนยันแบบนี้ แล้ววางแผนไฟล์/การทดสอบ/การย้ายฐานข้อมูล
2. พัฒนาแยกจากงานขายที่แก้ค้าง ทดสอบกับฐานข้อมูลทดสอบและข้อมูลจำลอง
3. ส่งหน้าเมนูและผลทดสอบให้ตรวจ พร้อม migration/config ที่เตรียมจริง
4. ตั้งค่า BOT และ webhook ของ BO ad จากบัญชีที่ผู้ใช้เปิดไว้ ทดสอบรับข้อความใหม่ก่อนเปิดตัดอัตโนมัติ
5. นำขึ้นระบบจริงเมื่อปลายทางและข้อมูลรับรองพร้อม ตรวจผลด้วยรายการทดสอบที่ตกลงก่อน แล้วส่งลิงก์ใช้งานและคู่มือ

สิ่งที่มีอยู่ตอนนี้: เว็บตัวอย่าง LINE/Sheets และตัวแยกข้อความจากงานเดิม ยังไม่เชื่อม MySQL/คลัง BO ad จึงไม่อ้างว่าตัดกระเป๋าจริงได้แล้ว
